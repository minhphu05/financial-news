# Local financial-news pipeline implementation plan

**Status (23/09/2026):** the original audit proposal has now been implemented through Phase 04 for the local financial-news slice. Phase 01 provides Bronze/Silver, Phase 02 provides Gold/Qdrant/DuckDB, Phase 03 provides Airflow orchestration, and Phase 04 provides a separate PostgreSQL → Debezium → Kafka metadata control plane. See [bronze-silver-local.md](bronze-silver-local.md), [silver-gold-local.md](silver-gold-local.md), [airflow-local.md](airflow-local.md), and [metadata-control-plane.md](metadata-control-plane.md) for measured evidence. The Phase 04 Kafka topics contain control metadata only; stock-market streaming remains future work.

## Scope and sequencing

Build from the checked-in CafeF snapshot toward independently runnable local jobs. Preserve the existing scraper, Prefect app, RAG API, frontend, and NER research while the new path is proven. Docker Compose is the local runtime; the cloud architecture is a migration target. Keep Kafka/Flink/market-price streaming, Kubernetes, Azure services, and crawling out of this news batch milestone. PostgreSQL metadata CDC through Debezium/Kafka is a later phase after orchestration. Introduce Airflow **after** all individual jobs and a complete replay work without it.

## Decisions to lock before implementation

1. **Canonical source:** use `cafef_news_raw_final.json` as the first batch. Older JSON/title files are references, not additive inputs. A later ingestion policy can accept genuinely new snapshots by checksum and source/date partition.
2. **Article identity:** source plus canonical URL is the primary key. Retain source `_id` only as lineage. Decide URL canonicalization and how a corrected article body supersedes an earlier version. Keep different URLs with equal content hash and flag them for review at first.
3. **Mention identity:** preserve all distinct article/ticker/keyword associations and their observation provenance. Establish how null ticker/keyword fields and repeated identical observations are represented.
4. **Publication time:** parse known CafeF patterns under an explicit site timezone policy; preserve the original string and mark invalid/ambiguous values. Do not use export `metadata.Date` as publication time by default.
5. **Storage layout:** set bucket/prefix names, Delta table paths, table version selection, checkpoint/log retention, and safe publication rules via configuration. Document MinIO/Spark hostnames for in-container and host access separately.
6. **Embedding:** choose a model/dimension for the local smoke test. The existing Voyage adapter is one option; a deterministic test embedder must allow full pipeline tests without an API key. Gold generation is independent of this choice.
7. **Serving publication:** choose verified Gold Parquet export or a supported direct Delta reader for DuckDB, and ensure a single committed version is pinned. Decide local `.duckdb` path and expected query views.

These are engineering decisions the implementation can resolve with measured local tests; they do not require deploying production infrastructure first.

## Meaningful verification gates

- **Schema and source tests:** exercise actual raw export keys (`ticket symbol`, `post date`, nested `metadata`), missing context, malformed date, URL host, Unicode normalization, and title/body preservation.
- **Deduplication test:** show that one URL observed for two tickers/keywords produces one article and both associations; an equal-content different URL remains traceable.
- **Replay/recovery test:** rerunning a stage against the same input/version produces the same logical output; a failed stage never changes the published pointer. A changed text/chunker version makes obsolete Qdrant points detectable.
- **Storage integration test:** read and write Delta on MinIO from the intended Spark image, including a restart and a second commit. This is the main environment risk and should be proven before building all jobs.
- **Projection reconciliation:** compare Gold article/chunk totals with DuckDB and Qdrant (when indexed). Check that a retrieval payload resolves to an existing Gold `chunk_id` and source URL.

Existing unit tests for text cleaning, chunking, quality rules, and Qdrant behavior can supply regression examples. Add focused tests for **every core transformation** and the new storage boundaries, using the representative raw fixture and meaningful failure cases. Do not treat Compose syntax validation or static imports as end-to-end proof.

## Repository changes expected later, not in this audit

Incrementally add a local pipeline package and job entry points, configuration for MinIO/Spark/Delta/PostgreSQL/Qdrant/DuckDB, minimal Compose services/profiles, storage contract tests, and a reproducible local run guide. Refactor only the existing utilities that provide demonstrated value. Update outdated Makefile/scripts and existing architecture/runbook pages when the new jobs actually run; do not relabel the current Prefect/Mongo flow as the new pipeline. Preserve crawler and research trees until a separate migration decision is made.
